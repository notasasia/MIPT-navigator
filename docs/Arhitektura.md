# Как строится инструкция

## Что изменилось

Раньше answer.py выбирал один из тематических маршрутов через регулярные выражения. В 14 наборах было 38 готовых рекомендаций. Новый обработчик использует гибридный поиск для каждого вопроса. Прежние формулировки и селекторы источников перенесены в tests/golden/reference_routes.json и служат эталонами. Производственный код этот файл не читает.

## От поиска до шага

1. PDF, DOCX и XLSX проходят через существующие парсеры. SQLite хранит оригинал и его фрагменты. Для загруженного документа дата извлекается из явно обозначенного грифа утверждения или подписания с датой в формате ДД.ММ.ГГГГ. В остальных случаях пользователь видит исходный файл и отметку о неизвестной дате.
2. Поиск BM25 и RuBERT учитывает дату и выбранный набор документов. Из ранжированного списка собираются основания, соседние пункты и явные ограничения области применения. Короткие новые регламенты могут поместиться в контекст целиком. Бюджет контекста ограничен.
3. Qwen получает пользовательский вопрос и пронумерованный набор отрывков. JSON-грамматика ограничивает форму вывода. Модель выбирает действия, исключения, условия и последовательность по локальным идентификаторам. Веса читаются через llama.cpp прямо в процессе Python. Для языка и форматов заявлены возможности в официальной карточке модели. https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF
4. Pydantic проверяет JSON. Для действия требуется идентификатор фрагмента из отправленного контекста, доступного пользователю на заданную дату. Код сопоставляет его с индексом SQLite. Текст существенного действия и условия переносится из проверенной выдержки. Метаданные источника добавляются из индекса. Такой подход сохраняет исходные сроки, исполнителей и формулировки. Он допускает канцелярский стиль и длинные шаги.
5. Явную зависимость от предыдущего пункта можно добавить, когда формулировка описывает последовательность и ссылается на соответствующий пункт. Ссылки вперёд, циклы и непрослеживаемые зависимости отбрасываются. Для шагов без явной зависимости порядок показа определяет модель. Условия, оставшиеся внутри текста шага, видны пользователю.
6. При неизвестной роли система может запросить уточнение. Ответ добавляется к предыдущему вопросу. Неполнота, отброшенные ссылки, отсутствующие приложения и расхождения выводятся отдельно. Для числовых расхождений проверяются одинаковые формулировки с различающимися величинами. При смысловом расхождении, замеченном моделью, показываются оба основания.
7. JSON содержит статус, шаги, условия, зависимости, оригинальные цитаты и координаты. Даты подписания, регистрации и вступления в силу различаются. Пустое значение означает отсутствие подтверждённого реквизита.

## Что требует проверки человеком

Даже действительная ссылка может быть нерелевантной вопросу. Проверка принадлежности цитаты источнику не доказывает полноту подобранных норм или их смысловую применимость. При большом корпусе поиск может пропустить исключение, а небольшая модель может неверно выбрать цитату или принять сходные положения за противоречие. Для значимых решений нужно открыть источники. Прототип не является полной системой версионирования нормативных актов.

## Выбор локального генератора

RuBERT-tiny используется как кодировщик поиска. Задачу отбора и упорядочения действий выполняет генеративная Qwen2.5-1.5B-Instruct. На доступной CPU-машине квантованный GGUF занимает 1 117 320 736 байт. Выбор оставляет память для RuBERT, индекса и Streamlit. Более крупные локальные модели требуют отдельного замера задержки и качества. Внешние API не входят в путь обработки документов. Установщик загружает публичные файлы весов и токенизатора.

## Дополнительная проверка гибридного поиска

После объединения BM25 и RuBERT в дальнейший отбор попадают как кандидаты со словесным совпадением, так и фрагменты с сильной семантической близостью без общих стемов. Для второго случая используется порог cosine 0,85. Это инженерный порог для текущей модели, а не оценка вероятности правильного ответа. Если веса локального cross-encoder установлены, он повторно сравнивает вопрос и фрагмент. Без его весов сохраняется гибридный режим. Для составного вопроса с союзом «и» перед вторым инфинитивом система ищет основания по каждой части. Когда обе части ведут к одному регламенту, в генератор поступает исходный вопрос целиком. Для разных регламентов результаты собираются отдельно и затем объединяются. Иные конструкции могут не разделиться.

Повторное ранжирование также сравнивает вопрос с содержанием пронумерованных пунктов. При извлечении процедур отбрасываются строки подписного листа, незаполненные шаблоны и обрывки табличных строк. После генерации можно восстановить пропущенное звено между выбранными шагами, если условие указывает на единственный полный пункт из контекста того же документа.

При запросе явно указанного номера приказа сначала проверяются его реквизиты среди документов на выбранную дату. Для отдельного запроса на поиск файла возвращается карточка документа с доступом к оригиналу. Даты до начала действия и документы за пределами выбранного корпуса исключаются. Специальный переход между архивным и новым регламентами ФЛС не представляет собой общее версионирование для всех документов.

Для некоторых конструкций вида «назначить права доступа» система ищет упоминание операции и её объекта в одной выдержке. Отсутствие такого сочетания приводит к консервативному отказу. Разные термины или разбивка одного правила по нескольким пунктам могут дать ложный отказ. Обратная проблема сохраняется: сама по себе дословная цитата не подтверждает применимость к конкретному вопросу.

## Изменения r3

Один запрос ограничивается ведущим документом и источниками, на которые явно ссылается первичная выдача. Отдельные намерения в составном вопросе сохраняют независимые области поиска. При явном исключении категории из одного варианта и её упоминании во втором выбирается подтверждённая ветвь. Та же ссылка хранит исходный текст целого пункта. Для вопросов об условиях допуска отбираются основания допуска, подачи и решения. Для общего порядка учитываются явно названные документы, действия передачи и согласования. После локального вывода Qwen проверка полноты восстанавливает найденные обязательные положения, пропущенные декодером. Для коротких и неизвестных документов продолжает использоваться исходный механизм Qwen и проверки ссылок.

Правила основаны на языковых конструкциях и структуре текста, без справочника маршрутов, номеров пунктов или названий файлов. Выбор ведущего документа может пропустить косвенно связанный документ, а синонимы и сложные области применимости могут не распознаться. Статус partial означает, что сохранились основания для ручной проверки. Система не вычисляет вероятность полноты. Примеры из набора разработки не служат независимой оценкой качества.
